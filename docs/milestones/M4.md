## Architecture Decisions

### WireframeEditor Modular Design
To avoid a monolithic 1500-line file, WireframeEditor is split into 5 composable modules:

```
lib/koalemos/lenses/wireframe_editor/
├── core.ex                    # Main lens interface, coordination (~250 lines)
├── dom_handler.ex            # HTML/DOM manipulation (~450 lines)
├── javascript_handler.ex     # JavaScript parsing/modification (~400 lines)
├── css_handler.ex            # CSS parsing/modification (~350 lines)
├── testing.ex                # Test utilities (~150 lines)
└── context.ex                # Context building (~100 lines)
```

**Benefits:**
- Single Responsibility: Each module handles one concern
- Testable: Modules can be tested independently
- Maintainable: Easier to understand and modify smaller files
- Composable: Can mix/match handlers for different use cases

### Tool Execution & Agent-as-Node Pattern

**Challenge:** WireframeEditor lens provides tools (query_element, add_element, modify_styles, etc.) that need execution infrastructure.

**Solution:** Implement tool execution in Sprint 7 with two approaches:

1. **Direct Tool Execution:**
   - Add ToolExecution step to routine loop (after LLMRequest, before ResponseParsing)
   - Simple tool calls execute immediately
   - Tool results added to context for next iteration

2. **Agent-as-Node Pattern** (inspired by flo's TemplatedSemanticAgent):
   - Sub-routine node within the main routine
   - Manages complex multi-step tool chains through an agent loop
   - Example workflow: "add a contact form"
     - Agent query_element → identifies insertion point
     - Agent generates HTML structure
     - Agent add_element → inserts form
     - Agent modify_styles → applies styling
     - Returns final state to main routine
   - Enables autonomous execution of complex operations
   - Agent has its own loop for tool orchestration

**Benefits:**
- Simple tools execute directly (efficient)
- Complex operations handled by sub-routine agent (powerful)
- Clear separation: main routine for conversation flow, agent-node for tool chains
- Mirrors flo's successful pattern

**Implementation:** Sprint 7 will build both patterns, choosing based on operation complexity.

### Design Decisions

**Why Test Infrastructure First?**
- Enables manual validation throughout development
- Reduces debugging time with interactive testing
- Provides realistic test data for development
- Similar to M3's successful `/test/screenshot` page

**Why Modular WireframeEditor?**
- Maintainability: Smaller files easier to understand
- Testability: Independent module testing
- Separation of Concerns: Each handler has clear responsibility
- Extensibility: Easy to add new handlers (e.g., SVG, Canvas)

**Why These 3 Lenses?**
- PersonaLens: Demonstrates context-driven behavior modification
- SequentialThinking: Demonstrates reasoning transparency
- WireframeEditor: Demonstrates complex multi-tool coordination

Together, these lenses showcase different lens capabilities and patterns for future lens development.
