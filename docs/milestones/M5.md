## Architecture Decisions

### TemplatedSemanticAgent Pattern

A reusable agent loop step that combines EEx templating with configurable lenses:

```elixir
routing: %{
  type: TemplatedSemanticAgent,
  config: %{
    template: """
    Analyze the user's request and choose the best path.

    User request: <%= List.last(@context[:messages])[:content] %>

    Choose the appropriate action.
    """,
    lenses: ["Koalemos.Lenses.SemanticTransition"]
  },
  transitions: [
    {:answer_directly, "Answer questions without making changes"},
    {:targeted_change, "Make a specific focused modification"},
    {:build_from_scratch, "Create new wireframe from scratch"}
  ]
}
```

**Benefits:**
- Eliminates code duplication (agent loop implemented once)
- Full context access via EEx templating
- Configurable lenses per step
- Works as complete sub-routine (pushes onto execution stack)

### SemanticTransition Lens

Enables agents to choose workflow transitions using natural language:

```elixir
defmodule Koalemos.Lenses.SemanticTransition do
  # Provides context showing available transitions with descriptions
  def provide_context(state)

  # Returns choose_transition tool
  def tools(_config)

  # Dynamically builds tool schema from parent routine's transitions
  def info(:choose_transition, context)

  # Executes transition choice, returns {:workflow_transition, {target, reason}}
  def execute(:choose_transition, params, _lens_state)
end
```

**How It Works:**
1. Reads parent routine's `transitions` list from execution stack
2. Filters for semantic transitions (description is string, not atom)
3. Builds dynamic tool schema with enum of valid choices
4. Returns `workflow_transition` in lens_state when agent chooses
5. Engine pops execution stack and applies transition at parent level

### Lens Scoping & Hierarchy

**Problem:** Need proper lens inheritance and scope isolation across routine branches

**Solution:** Three-level lens configuration system:

1. **Base Lenses:** Inherited from parent context (workflow-level lenses)
2. **Config Lenses:** Specified in step config (step-level overrides/additions)
3. **Merged Lenses:** Result of merge-with-override semantics

**Merge Semantics:**
- Config lenses merge with base lenses (not replace)
- Same module name → config overrides base
- New module name → added to base
- Unmentioned modules → retained from base

**Scope Isolation:**
- First sub-routine in workflow saves `_routine_base_lenses`
- Steps with config lenses: merge config with saved base
- Steps without config lenses: restore to saved base
- Prevents lens modifications from leaking across branches

**Example:**
```elixir
# Initial context has: [WireframeEditor, SequentialThinking]

# Routing step configures:
lenses: [
  ["WireframeEditor", %{readonly: true}],  # Override with readonly
  "SemanticTransition"                      # Add new lens
]
# Result: [WireframeEditor (readonly), SequentialThinking, SemanticTransition]

# Next step has no config
# Result: Restores to [WireframeEditor, SequentialThinking]
```

## Lessons Learned

1. **Semantic > Fixed Phases:** Users think in terms of "what they want to do" not "which phase to be in"
2. **Early vs Late Binding:** Don't ask agent what to do next when you already know the steps
3. **Scope Isolation Critical:** Without it, lens modifications leak across branches causing confusion
4. **Merge > Replace:** Config lenses enhance rather than replace base lenses
5. **EEx Powerful:** Full context access in templates enables rich agent prompting
6. **Two-State Model:** Seeing both designed and running state is valuable for testing workflows
7. **Screenshot Limitations:** Anti-loop instructions needed when rendering not pixel-perfect
8. **Pattern Clarity:** Clear separation of semantic routing vs linear playbooks prevents confusion
